# ADR 0004 — Grille de notation transparente et réglable

Date : 02/11/2026 · Statut : accepté

## Contexte

Sprint 4 : jusqu'ici l'IA donnait une note brute « au jugement » et des pénalités fixes (−0,5, −1) tirées d'une grille Markdown. La note était peu reproductible, ses raisons peu lisibles, et tout changement de priorité obligeait à renoter les offres à la main. L'utilisateur veut voir et régler les critères (poids, barèmes, règles) dans un panneau, et que les notes suivent.

## Décisions

1. **L'IA note des critères, l'application calcule la note.** L'IA donne des sous-notes de 0 à 10 (avec justification) pour les critères marqués `ia`, signale les règles bloquantes qui s'appliquent et, quand l'offre les donne, les données d'entrée des critères calculés (jours sur site, salaire). L'application calcule tout le reste. Un champ `note` envoyé avec `criteres` est ignoré et signalé (`avertissements`).
2. **Calcul (fonction pure `calculerNote`, `src/core/grille.ts`)** : sous-notes des critères calculés depuis les barèmes ; moyenne pondérée, poids normalisés (somme ramenée à 1) ; puis règles bloquantes dans l'ordre (`zero` → 0, `plafond` → min) ; arrondi au demi-point (`Math.round(x × 2) / 2`, 4,25 → 4,5). Un critère IA absent vaut 5 avec un drapeau ; un critère calculé sans donnée vaut la valeur « inconnu » du barème (5) avec un drapeau ; une règle inconnue ou désactivée est ignorée et listée. Une nouvelle saisie est validée plus strictement (`verifierSaisie` : critère ou règle inconnus refusés, critère calculé noté par l'IA refusé).
3. **Barèmes.** Télétravail : six valeurs pour 0 à 5 jours sur site, plus « inconnu ». Jours lus dans la saisie, sinon dans le texte libre `teletravail` de l'offre (« 3 j sur site », « 2 j de télétravail » → 3, « full remote » → 0, « sur site » → 5 ; « hybride » seul → inconnu). Rémunération : deux paliers (salaire en K€/an, TJM en €/j), plancher → 5, cible haute et au-delà → 10, sous le plancher → 0, linéaire entre les deux ; plancher propre au full remote facultatif ; valeur retenue d'une fourchette réglable (milieu par défaut). Un salaire mensuel compte × 12, un taux horaire × 7 ; un salaire annuel sous 1 000 est lu en K€. L'unité choisit le palier (`an` / `mois` → salaire, `jour` / `heure` → TJM). La cible basse n'entre pas dans le calcul : c'est un repère montré à l'IA et dans le panneau.
4. **Valeur exacte et valeur affichée.** `notes.note` (et donc `offres.note`, triée et filtrée) porte l'arrondi au demi-point, celui qu'on affiche : le filtre « ≥ 4,5 » donne ce qu'on voit. La valeur exacte est dans `notes.note_exacte` ; `note_brute` reçoit la moyenne pondérée et `penalites` le libellé des règles appliquées, pour la compatibilité avec les vues existantes.
5. **Stockage (migration 0004).** La grille est un fichier du dossier de données, `<données>/profil/grille.json`, validé par un schéma Zod strict (une clé inconnue est une erreur, pour attraper les fautes de frappe d'une édition à la main). Chaque enregistrement crée une version dans la table `grilles` (version, contenu JSON, date, auteur `interface` | `cli` | `mcp` | `fichier`, résumé) ; le fichier reflète la version courante (métadonnées `version`, `modifiee_le`, `resume` en tête). Les notes gagnent `note_exacte`, `saisie` (sous-notes, entrées, règles signalées : de quoi recalculer), `decomposition` (résultat complet : sous-notes, poids, contributions, règles, drapeaux, entrées utilisées) et `recalculee_le`. Pas de table `sous_notes` : la décomposition se lit et s'écrit d'un bloc, et ne sert jamais de filtre.
6. **Synchronisation fichier / base** à chaque lecture de la grille : base vide + fichier → version 1 (auteur `fichier`) ; fichier modifié à la main → nouvelle version `fichier` et renotation ; fichier supprimé → réécrit depuis la base. Comparaison sur la forme canonique validée (la mise en page du fichier ne compte pas).
7. **Renotation instantanée, sur place.** Un changement de grille recalcule la dernière note de chaque offre qui a une `saisie`, sans relire d'offre, dans la même transaction que l'insertion de la version. La note est mise à jour sur place (pas de nouvelle ligne d'historique : la saisie n'a pas changé, et la version de grille appliquée est notée dans `grille_version`) ; seules les offres dont la note affichée change voient `offres.note` recalculée. Les anciennes notes globales (sans `saisie`) restent figées, badge « ancienne grille ».
8. **Aperçu avant d'enregistrer** (`apercuGrille`) : même calcul sans écriture ; nombre d'offres qui changent, offres qui franchissent le seuil (ancien seuil avant, nouveau seuil après), les 100 plus grands changements. Le panneau le demande au serveur à chaque réglage (après 350 ms) ; les exemples de référence sont recalculés dans le navigateur (le module de calcul n'a pas de dépendance Node).
9. **Correction à la main** (`modifierSousNotes`) : part de la dernière note, remplace les sous-notes, entrées ou règles modifiées, et ajoute une note à l'historique (origine `interface`) ; chaque sous-note garde son origine (`ia` ou `interface`). Elle vaut aussi pour passer une ancienne note globale en note à critères.
10. **Restauration** : le contenu d'une ancienne version devient une nouvelle version (l'historique ne se réécrit pas).
11. **MCP** : `grille` (grille + consignes de notation générées depuis la grille + format attendu + notes calculées des exemples), `modifier_grille` (changement partiel, `essai` pour l'aperçu, `restaurer_version`), `renoter`, `historique_grille` ; `noter_offre` / `noter_lot` acceptent `criteres`, `entrees`, `bloquants` (et `essai` pour le lot). Les consignes demandent à l'IA de ne modifier la grille qu'à la demande de l'utilisateur, après un essai.
12. **Exemple générique** dans le dépôt (`exemples/grille.json`, sociétés fictives), copié par `cap-emploi grille --init`.

## Conséquences

- La note change de nature : une offre hors cible dont le télétravail et le salaire sont inconnus reste vers 3 (les valeurs neutres pèsent 40 %), là où l'ancienne grille donnait 0 à 1. Le classement au-dessus du seuil reste juste ; si l'utilisateur veut des notes basses plus franches, une règle « stack hors inventaire » (plafond) ou un poids technique plus fort le permettent sans toucher au code.
- Les 193 notes reprises de l'historique restent des notes globales : elles ne bougent plus avec la grille. Les renoter demanderait de relire les offres (à faire au fil des lots, ou offre par offre dans l'interface).
- Le fichier `grille-notation.md` de l'utilisateur n'est plus lu par l'application ; la grille JSON fait foi pour le calcul.
