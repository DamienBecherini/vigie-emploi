# ADR 0004 — Transparent and adjustable scoring grid

**English** · [Français](0004-scoring-grid.fr.md)

Date: 02/11/2026 · Status: accepted

> The tool, field and command names quoted are those of the time, in French; the code and the API have since moved to English (for example `ajouter_evenement` → `add_event`, `noter_lot` → `score_batch`, `grille` → `rubric`).

## Context

Sprint 4: until now the AI gave a raw score "by judgement" and fixed penalties (−0.5, −1) taken from a Markdown grid. The score was hard to reproduce, its reasons hard to read, and any change of priority meant rescoring the offers by hand. The user wants to see and adjust the criteria (weights, scales, rules) in a panel, and wants the scores to follow.

## Decisions

1. **The AI scores criteria, the application computes the score.** The AI gives sub-scores from 0 to 10 (with a justification) for the criteria marked `ia`, reports the blocking rules that apply and, when the offer gives them, the input data of the computed criteria (days on site, salary). The application computes everything else. A `note` field sent with `criteres` is ignored and reported (`avertissements`).
2. **Computation (pure function `calculerNote`, `src/core/grille.ts`)**: sub-scores of the computed criteria from the scales; weighted average, normalised weights (sum brought back to 1); then blocking rules in order (`zero` → 0, `plafond` → min); rounding to the half point (`Math.round(x × 2) / 2`, 4.25 → 4.5). A missing AI criterion counts as 5 with a flag; a computed criterion without data takes the "unknown" value of the scale (5) with a flag; an unknown or disabled rule is ignored and listed. A new input is validated more strictly (`verifierSaisie`: unknown criterion or rule refused, computed criterion scored by the AI refused).
3. **Scales.** Remote work: six values for 0 to 5 days on site, plus "unknown". Days read from the input, otherwise from the offer's free-text `teletravail` field ("3 j sur site", "2 j de télétravail" → 3, "full remote" → 0, "sur site" → 5; "hybride" alone → unknown). Pay: two tiers (salary in K€/year, daily rate in €/day), floor → 5, high target and above → 10, below the floor → 0, linear in between; optional separate floor for full remote; adjustable value taken from a range (middle by default). A monthly salary counts × 12, an hourly rate × 7; an annual salary under 1,000 is read in K€. The unit chooses the tier (`an` / `mois` → salary, `jour` / `heure` → daily rate). The low target does not enter the computation: it is a reference point shown to the AI and in the panel.
4. **Exact value and displayed value.** `notes.note` (and therefore `offres.note`, sorted and filtered on) holds the value rounded to the half point, the one displayed: the "≥ 4.5" filter gives what one sees. The exact value is in `notes.note_exacte`; `note_brute` receives the weighted average and `penalites` the label of the rules applied, for compatibility with the existing views.
5. **Storage (migration 0004).** The grid is a file in the data folder, `<données>/profil/grille.json`, validated by a strict Zod schema (an unknown key is an error, to catch typos in a hand edit). Each save creates a version in the `grilles` table (version, JSON content, date, author `interface` | `cli` | `mcp` | `fichier`, summary); the file reflects the current version (metadata `version`, `modifiee_le`, `resume` at the top). Scores gain `note_exacte`, `saisie` (sub-scores, inputs, reported rules: what is needed to recompute), `decomposition` (full result: sub-scores, weights, contributions, rules, flags, inputs used) and `recalculee_le`. No `sous_notes` table: the breakdown is read and written as one block, and is never used as a filter.
6. **File / database synchronisation** on each reading of the grid: empty database + file → version 1 (author `fichier`); file modified by hand → new `fichier` version and rescoring; file deleted → rewritten from the database. Comparison on the validated canonical form (the layout of the file does not count).
7. **Instant rescoring, in place.** A change to the grid recomputes the latest score of each offer that has a `saisie`, without re-reading any offer, in the same transaction as the insertion of the version. The score is updated in place (no new history row: the input has not changed, and the grid version applied is recorded in `grille_version`); only the offers whose displayed score changes have `offres.note` recomputed. The old overall scores (without `saisie`) stay frozen, with an "old grid" badge.
8. **Preview before saving** (`apercuGrille`): same computation without writing; number of offers that change, offers that cross the threshold (old threshold before, new threshold after), the 100 largest changes. The panel requests it from the server on each adjustment (after 350 ms); the reference examples are recomputed in the browser (the computation module has no Node dependency).
9. **Manual correction** (`modifierSousNotes`): starts from the latest score, replaces the modified sub-scores, inputs or rules, and adds a score to the history (origin `interface`); each sub-score keeps its origin (`ia` or `interface`). It also serves to turn an old overall score into a criterion-based score.
10. **Restoring**: the content of an old version becomes a new version (the history is not rewritten).
11. **MCP**: `grille` (grid + scoring instructions generated from the grid + expected format + computed scores of the examples), `modifier_grille` (partial change, `essai` for the preview, `restaurer_version`), `renoter`, `historique_grille`; `noter_offre` / `noter_lot` accept `criteres`, `entrees`, `bloquants` (and `essai` for the batch). The instructions ask the AI to change the grid only at the user's request, after a trial run.
12. **Generic example** in the repository (`exemples/grille.json`, fictitious companies), copied by `vigie-emploi grille --init`.

## Consequences

- The score changes in nature: an off-target offer whose remote work and salary are unknown stays around 3 (the neutral values weigh 40 %), where the old grid gave 0 to 1. The ranking above the threshold stays correct; if the user wants clearer low scores, a "stack outside the inventory" rule (cap) or a heavier technical weight allows it without touching the code.
- The 193 scores imported from the history remain overall scores: they no longer move with the grid. Rescoring them would mean re-reading the offers (to be done as batches come in, or offer by offer in the interface).
- The user's `grille-notation.md` file is no longer read by the application; the JSON grid prevails for the computation.
